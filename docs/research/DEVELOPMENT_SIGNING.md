# TouchBridge development signing

Build and install at the stable path:

```sh
./scripts/build_dev_app.sh --install
open "$HOME/Applications/TouchBridge Dev.app"
```

When the app is already running, use `./scripts/build_dev_app.sh --install --restart`.
This builds and verifies the replacement first, requests normal termination of
only the installed app, waits for it to quit, then replaces and reopens it.
Without `--restart`, installation refuses to replace a running instance.

The identifier stays `com.antigravity.touchbridge.dev`. Use the installed copy
for permission grants and physical testing. A shell-launched CLI can inherit
privacy attribution from its host; it does not prove the GUI app's grant.

## Signing policy

`build_dev_app.sh` requires a certificate and private key in the user's Keychain.
It never falls back to ad-hoc signing. First use prefers an identity named
`TouchBridge Dev Local Signing`, otherwise selects the sole valid code-signing
identity. With multiple choices, select explicitly:

```sh
security find-identity -v -p codesigning
TOUCHBRIDGE_SIGNING_IDENTITY=<40-character-certificate-SHA1> ./scripts/build_dev_app.sh --install
```

The successful fingerprint is saved in
`~/Library/Application Support/TouchBridge/Development/signing-identity.sha1`.
This contains no private key. Subsequent builds require that identity; a locked,
missing, or expired certificate fails before installation. Unlock the Keychain
if necessary. `TOUCHBRIDGE_CONFIG_DIR` can isolate configuration for testing.

On this owner's machine an existing Apple Development identity was available,
so creating another certificate was unnecessary. Its current expiry is June 15,
2027. No subscription, notarization, or distribution certificate was obtained.
The identity must remain available; after renewal select the new fingerprint
explicitly. Installation checks the candidate against the installed designated
requirement and refuses an incompatible certificate change. Deliberate identity
migration requires preserving/moving the old app first, then authorizing the new
identity once; do not weaken the requirement to an identifier alone.

For a machine without a signing identity, no Apple Developer membership is
required: in Keychain Access, use Certificate Assistant → Create a Certificate,
name it `TouchBridge Dev Local Signing`, select Self Signed Root and Code Signing,
and store the persistent certificate/private key in the login Keychain. If it
isn't valid for code signing, set that certificate's Code Signing trust policy
in the user Keychain to Always Trust. Do not change system roots or other trust
policies. Verify it appears in `security find-identity -v -p codesigning`, then
run the build script. Keep the identity rather than recreating it every build.
This alternative was documented, not provisioned or tested on this machine.

The default certificate-based designated requirement is generated by `codesign`
and checked after signing. It must not contain a `cdhash` constraint. Local
certificates typically bind the certificate hash and bundle identifier; Apple's
Development certificate uses Apple's chain and developer identity. The script
prints and saves the actual requirement in `build/dev/designated-requirement.txt`.
A Gatekeeper rejection from `spctl` is a separate distribution-policy assessment,
not an Accessibility permission test. This workflow is for local development.

## Installation safety

Both the build bundle and installation are staged and signature-verified before
replacement. Existing bundles are moved into unique `.touchbridge-backup.*`
directories alongside their previous location. A failed publication attempts to
restore the previous path. Backups are retained, never pruned automatically;
remove unwanted backups yourself only after testing. No TCC reset is run.

## Check the actual app's permission

With the normal app stopped, launch this read-only diagnostic through LaunchServices:

```sh
open -n -W "$HOME/Applications/TouchBridge Dev.app" --args \
  --permission-status --permission-status-output /tmp/touchbridge-permission.json
cat /tmp/touchbridge-permission.json
```

It reports the exact bundle, executable path, PID, and `AXIsProcessTrusted()` as
`accessibilityTrusted`. It exits without requesting permission, acquiring HID,
or starting interaction. Direct execution with `--permission-status` also works,
but can have different TCC attribution. The menu app logs its path/PID/trust on
startup and rechecks trust every two seconds without prompting. It starts with
touch disabled, as before; enable it when ready for physical testing.

## One-time migration from ad-hoc signing

The inherited signature had a hash-only requirement. On September 27, 2026,
`tccd` logged `Failed to match existing code requirement` for this bundle's
Accessibility service after rebuilds. A Settings toggle can remain enabled for
an old identity while the rebuilt process is denied. An unchanged path or bundle
identifier alone does not repair that mismatch.

After installing the certificate-signed app, reauthorize that exact installed
copy in System Settings → Privacy & Security → Accessibility. If necessary,
remove only TouchBridge Dev's stale entry and add the installed copy again.
Quit and reopen the app, then use the LaunchServices diagnostic above.

Only if that fails, the narrow reset command is:

```sh
tccutil reset Accessibility com.antigravity.touchbridge.dev
```

This revokes only this bundle's Accessibility grant, requiring a new owner grant.
It is an owner-run last resort, never part of the build script. Do not reset All
or other privacy services. TCC logs also showed a ListenEvent identity mismatch;
no Input Monitoring setting was changed by this work.

Verify retention by recording `accessibilityTrusted: true`, rebuilding/installing,
and checking a new LaunchServices process again. An unchanged designated
requirement or passing `codesign` alone does not establish TCC retention.

## Validation and physical acceptance

Run `swift build`, `.build/debug/TouchBridgeProbe --test-runtime`, and
`.build/debug/TouchBridgeProbe --test-architecture`. Run them from a scratch
working directory if you want to preserve the inherited evidence JSON.

The inherited P3-06/P3-06R scratch harnesses use fixed screen coordinates and
reimplement momentum math, including simulated cancellation. Their pass labels
are not proof of the production gesture pipeline or owner-perceived momentum.
The runtime/architecture suites exercise production classes; physical acceptance
still requires slow drags, ordinary/fast flicks, new-touch interruption, real
mouse precedence, and more conservative Brave coasting. Double-click and drag/drop
remain separate future tasks.

References: [Apple TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html)
explains designated requirements and self-signed local identities;
[Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)
explains how privacy grants track code identity.
